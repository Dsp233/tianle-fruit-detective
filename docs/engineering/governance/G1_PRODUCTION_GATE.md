# AMC8 生产质量门禁启用收据

本次候选锁定已验证的 Git 树 `a25e0fbe7857b3b12ab5aef3a8ad6c79d285b78a`。从该树新增检查器、只读工作流和本收据。GitHub 作业核对测试合并的两个父提交及完整路径差异。任何其他新增、删除或修改的路径都失败，包括题库、运行产物、学习存储、历史兼容和已冻结的输入锁。此规则只适用于以下证据支持的候选。后续候选的变更须先完成适用验证、独立复核和新身份登记。

- [#70 源构建](https://github.com/Dsp233/tianle-fruit-detective/pull/70) 与 [#71 模块边界](https://github.com/Dsp233/tianle-fruit-detective/pull/71) 继承已授权的一次性替代验收。私有源码托管原生构建保留 `NOT_RUN`。四次离线构建使用同一执行环境的独立检出，私有源码在托管环境的供应和执行仍无直接验证。
- [#72 质量基础](https://github.com/Dsp233/tianle-fruit-detective/pull/72) 绑定隔离候选的冻结字节、只读权限、拒绝样例和双浏览器回归。生产验收的独立授权与此前的工程验收分别登记。

## 管理员启用顺序

1. 审阅本次正反 PR 作业，核对测试合并、当前 main、放行的精确候选 SHA 及已有 W1 回退证据。首度安装需要明确批准基线变更。从尚无门禁代码的 main 发起的作业会报告待安装并失败。
2. 在隔离目标验证规则，再将已批准规则应用到精确的 `refs/heads/main`。要求 PR、当前基线上的必需检查 `AMC8 verified production identity`、独立审查，以及对最后一次可审查提交的批准。将检查来源绑定 GitHub Actions，核实禁止非授权直推、强推和删除。门禁工作流及其可信脚本的改动需要受信审查者审核，限制绕过主体。若仓库可用的规则无法约束同名检查冒充或控制文件修改，应采用组织级受信工作流或独立 GitHub App，并保留阻断状态。
3. 回读生效的 ruleset 或分支保护，绑定正确检查、来源、角色和例外。用受控正反 PR 观察 GitHub 的合并可用性，以实际拒绝普通写入、旧 SHA、缺失检查和非授权例外作为生产强制验收证据。门禁启用前的托管作业只证明检查器判定。
4. 版本发布沿用 G0-X 的明确源 SHA、产物和公开验收授权。生产回退用单独审核的反向变更，绑定明确的上一版本与验证证据；紧急例外仅交获授权管理员处理并留审计记录。回退门禁配置时只移除本次规则并核对原设置。

本次演练的目标为独立候选分支。main 执行阶段从 PR 的 base Git 对象读取校验脚本。GitHub Actions 的 status 来源绑定需要与工作流审查规则共同生效。此前核对的 36 个声明写权限 job 仍涉及旧候选的受限分支写入，权限治理全仓任务继续等待真实受控写入与回退验证。
